## 1. 快速开始

### 1.1 安装

```bash
python -m venv .venv
.venv\Scripts\activate            # Windows
# source .venv/bin/activate       # Linux / macOS
pip install -r requirements.txt
```

| 依赖 | 说明 |
|---|---|
| `gmssl==3.2.2` | **版本必须固定**，3.2.1 加密布局不同 |
| `requests` / `tqdm` / `pycryptodome` / `pillow` | 必装 |
| `opencv-python` | 可选，仅视频人脸源需要 |

### 1.2 第一次运行

```bash
python panel.py
```

浏览器自动打开 `http://127.0.0.1:8765/`。

### 1.3 推荐流程

```
配置信息  →  历史记录  →  选择路线  →  上传预检  →  开始上传
```

**建议先拉取一次自己的历史数据**，再从中选表回放——自己的轨迹比仓库示例更贴合实际。

## 2. 图形界面

`panel.py` 是本地单页工作台，替代旧的 `web.py`。

> **已验证范围**：只有**合肥工业大学 fch 校区 + 打表模式**经过完整实测。
> 其他校区同样可选，但未验证。**合成轨迹、人脸核验请用 `python main.py`。**

左侧导航五步，按顺序走完即可完成一次上传。

### 2.1 配置信息

**多用户管理**：每个用户一份独立配置文件 `configs/<名字>.ini`，互不影响。

- 首次启动自动把 `config.ini` 复制成 `configs/user.ini`（默认用户 `user`）
- 点「添加用户」输入名称即可新建（中英文/数字/`_`/`-`，1~24 字）
- 新建用户的身份字段（token/device_id 等）自动清空，避免误用他人凭据
- 点卡片切换当前用户；`user` 不可删除
- **页面右侧浮窗**始终显示当前用户，预检页与上传页也会标明

> **只需填写 `[User]` 段**：`token`、`device_id`、`device_name`、`sys_edition`。
> `[Yun]` 的密钥与服务器、`[Run]` 的跑步参数、`[Login]` **保持原样**，
> 改错会直接导致上传失败。

- 敏感字段显示为掩码，**留空即不修改**
- 保存后只写回真正变化的键，并在界面列出改动项

`configs/` 已加入 `.gitignore`，各人凭据不会进仓库。

### 2.2 历史记录

从服务器拉取以前的跑步记录，保存为本地任务表。

1. 选择学期（自动加载）
2. 表格显示每条记录的结束时间、里程、任务名称
3. 点「拉取并保存」→ 保存为 `tasks_else/tasklist_N.json`
4. 右侧显示摘要：时间、里程、配速、步频、用时、踩点数、轨迹点
5. 点「刷新任务表列表」后，可在「选择路线」里选中该表

编号自动续接，不覆盖已有文件。功能等同命令行 `python history.py`。

> **任务表不绑定用户**：拉取到的 `tasks_else/tasklist_N.json` 所有用户共用。
> 历史记录本身是按**当前用户**的 token 拉取的，切换用户后看到的是各自的数据。

### 2.3 选择路线

选择校区目录与任务表，右侧地图叠加显示：

| 颜色 | 含义 |
|---|---|
| 蓝色折线 | 轨迹 |
| 绿色圆点 | 已踩点（`marked=Y`） |
| 橙色圆点 | 未踩点 |

**底图是高德瓦片（GCJ-02）**。任务表坐标本身就是 GCJ-02，两者同一坐标系，
不做任何转换即可对齐。换成 OpenStreetMap 等 WGS-84 底图会偏移约 500 米。

### 2.4 轨迹自然化（可选）

把选中的任务表形变成一条**形状不同**的新轨迹，生成新任务表后再预检。

> ⚠️ **算法能力有限，不能保证规避风控。**
> 本步骤只改变轨迹的几何形状与节奏，无法保证服务端不复核、不判定异常。
> 同一来源反复使用仍可能保留可识别相似性；是否使用、用几次，请自行判断并承担风险。

**操作**：选择强度 → 可选目标里程 / 随机种子 → 点「生成新轨迹」→
地图上灰色虚线是原轨迹、蓝色实线是新轨迹 → 「保存并使用」写入
`tasks_else/<名称>.json` 并自动切换到该表。

**生成时强制满足学校要求**，不满足会自动换种子重抽（最多 8 次）：

| 校验 | 判据 |
|---|---|
| 里程 | 不超过 `max_mileage_km`（目标里程超限时自动压到上限） |
| 步频 | 逐包 `runSteps` 与汇总 `recodeCadence` 都在 40~300 |
| 踩点 | 标记数 ≥ `min_dislikes`，且轨迹**实际经过**这些打卡点（半径 20m） |

连续 8 次都不满足会报错并给出最后一次的原因，不会产出不合规的任务表。

**临时文件自动清理**：保存的表登记为临时文件，**上传成功后自动删除**；
上传失败则保留，便于排查。也可以在上传成功面板里看到删除结果。

| 档位 | 偏离中位 | 包围盒外扩 | 适用 |
|---|---|---|---|
| 轻度 | 约 1.5 m | < 4 m | 最保守，几乎贴着原轨迹 |
| **中度** | **约 3.5 m** | **< 10 m** | **默认推荐** |
| 较强 | 约 6 m | < 18 m | 需要明显不同，仍在场地内 |

档位标定依据：合工大翡翠湖操场实测包围盒 **82~120m × 166~190m**，
真人轨迹本来就贴着跑道边缘。三档都保证形变后轨迹不会跑出场地
（`test_natural_output_stays_within_field` 钉住这条约束）。

**算法做了什么**（`yun_route.deform_points`）：

1. **航向扰动**：沿弧长推进的 OU 角度场，逐点旋转切线方向后重新积分。
   这是改变**形状**的关键——拐弯位置、曲率序列都变了，而不只是整体平移。
2. **法向 OU 游走**：沿法线方向低频摆动（跨道），限幅 ±10~20m。
3. **二维相关漂移**：x/y 各一个 OU 过程，模拟 GPS 大范围偏移。
4. **稀疏偶发跳变**：约 1.5 次/km，指数衰减，模拟信号跳点。
5. **节奏重采样**：等时间 + 等里程，配速/步频/里程三向自洽。

起点固定在原轨迹起点（跑步总从同一处出发），误差随距离累积。
**踩点信息从源表继承**，因此生成后可直接预检。

### 2.5 上传预检

用**假传输**把整条链路完整跑一遍，**不联网**：

```
getHomeRunInfo → start → splitPointCheating × N → isStandard → 尾批 → finish
```

**请求明细**（左侧）：逐个列出将要发出的请求，点开可看完整请求体 JSON。
每个 split 包标注点数、本包里程、平均步频、步幅、配速。

**学校要求对照**（右侧）：要求值 vs 本次实际值，带绿/红徽章。

| 项目 | 要求 | 本次提交 | |
|---|---|---|---|
| 总里程 | ≤ 2.00 km | 2.00 km | 满足 |
| 平均步频 | 40 ~ 300 spm | 163 spm | 满足 |
| 踩点数 | ≥ 3 个 | 2 / 5 个 | 不满足 |

**校验结论**：列出需要注意的问题。踩点不足会在 `start` 之前就失败，
此时没有请求体，但对照表仍会给出差距。

### 2.6 开始上传

确认预检结果后，勾选确认框 → 点「开始上传」。

上传过程中：

- **实时日志**：与终端输出完全一致（`main.py` 的 print 也被捕获）
- **进度条**：按已上传点数推进，不会超过 100%
- **成功面板**：完成后显示总里程、配速、步频、踩点数、时长、批次

服务端进程持有发送计划，前端无法凭任意参数调起上传——必须先预检，
且校区+任务表必须与预检一致。

## 3. 命令行

图形界面不是必需的，所有功能都能在命令行完成。

```bash
python main.py                              # 交互式
python main.py -a -t tasks_fch              # 打表全自动
python main.py -f cfg.ini -a -t tasks_fch   # 指定配置文件
python main.py --route-config examples/routes/deform_xc.json   # 合成轨迹
python main.py --dry-run                    # 离线演练
python history.py                           # 拉取历史记录
python live_probe.py <跑步区域>              # 准入探测（只读）
```

| 参数 | 说明 |
|---|---|
| `-f, --config_path` | 配置文件路径（缺省项目根 `config.ini`） |
| `-t, --task_path` | 任务表目录（缺省 `tasks_fch`） |
| `-a, --auto_run` | 全自动，不询问确认 |
| `-d, --drift` | 老式漂移（**已弃用**，仅 0.1mm 刚性平移） |
| `--route-config` | 合成轨迹配置，不能与 `-t`/`-d` 混用 |
| `--dry-run` | 离线演练，零网络 |
| `--face-photo` / `--face-video` | 人脸源 |
| `--face-detection` | 人脸检测标注 JSON |

**路径契约**：显式传入的相对路径按**调用时的工作目录**解析；
未显式传入的缺省资源按**项目根目录**解析。

## 4. 配置 config.ini

### 4.1 `[Yun]` — 服务器与密钥

| 键 | 说明 |
|---|---|
| `school_host` | 学校服务端地址。**会变**，用 `tools/getUrl_Id.py` 查询后写入，不要猜端口 |
| `school_id` | 学校 ID |
| `school_login_url` | 登录路径，如 `appLoginHGD` |
| `app_edition` | 客户端版本，应与当前 APK 一致（基线 `3.6.6`）。偏低会触发 `code=500` |
| `platform` | 固定 `android` |
| `md5key` | sign 计算用的 appsecret |
| `publickey` / `privatekey` | SM2 密钥对。仓库默认值**公私不配对**，生产加密只需要公钥 |
| `cipherkey` / `cipherkeyencrypted` | 登录/学校目录旧路线的固定 SM4 key 与其密文 |

### 4.2 `[User]` — 账号与设备

| 键 | 说明 |
|---|---|
| `token` | 登录令牌。留空时会询问账号密码登录 |
| `device_id` | 请求头 `deviceId`。真机是 android_id 的 SHA-256（64 位小写 hex） |
| `device_name` | 格式为 `厂商(型号)`，如 `Xiaomi(M2011K2C)` |
| `sys_edition` | 系统版本裸值，如 `15`。finish 体的 `sysEdition` 会自动加 `Android_` 前缀 |
| `sys_version` | 可选，优先于 `sys_edition` 用于 `sysVersion` 头 |
| `legacy_uuid` | 设为 `true` 时沿用配置固定 uuid（旧路线）；默认每请求随机 |

### 4.3 `[Run]` — 跑步参数

| 键 | 默认 | 说明 |
|---|---|---|
| `split_count` | 10 | 每批上传点数（服务端下发 `passPointNum` 时以服务端为准） |
| `max_mileage_km` | 2.0 | **本地里程硬上限**，到点截断并结束。0 = 不限制 |
| `min_dislikes` | 3 | **学校要求的最少踩点数**，与任务下发值取大。0 = 只按任务下发值 |
| `single_mileage_min/max_offset` | 0 | 里程区间的**收紧量**，应为 0 |
| `cadence_min/max_offset` | 0 | 步频区间的**收紧量**，应为 0 |
| `strides` | 0.8 | 步幅（米），仅在任务表无步数时用于派生 |
| `min_distance` | 2.5 | 自动打表模式的目标里程 |

> ⚠️ **四项 offset 必须是 0。** 它们用来**收紧**学校下发区间，
> 非 0 会让合法数据被判越界。历史配置的 `0.5 / -0.5 / 30 / -150`
> 会把 120~190 的步频区间收缩成 `[150, 40]`（空区间），**任何数据都被拒**。

#### `max_mileage_km` — 本地里程硬上限

学校规定"一次只能跑 2km"时设为 `2.0`：

- 取**本地值与学校下发 `raSingleMileageMax` 的较小者**
- 跑到上限时在最后一段线路上**精确截断**，末点里程恰好等于上限
- 随即进入结束链：`isStandard → 尾批 → finish`
- 启动时打印确认：`[里程上限] 本地硬上限 2.000 km 小于学校下发 3.000 km`

#### `min_dislikes` — 学校要求的最少踩点数

判据是 `max(任务下发 raDislikes, min_dislikes)`——学校要求更严按学校，
服务端下发更多按服务端。不足时 `start` 前直接报错。

## 5. 打表模式

直接回放一张已有的任务表，是目前**最稳定、最推荐**的方式。

### 5.1 完整链路

```
getHomeRunInfo → 校验 → start → splitPointCheating × N → isStandard → 尾批 → finish
```

`start` 之前做三项校验，任一不满足就**在建记录之前**报错：

| 校验 | 判据 |
|---|---|
| 里程 | 实际上报里程（上限截断后）落在 `[raSingleMileageMin, raSingleMileageMax]` |
| 步频 | 整表平均步频落在 `[raCadenceMin, raCadenceMax]` |
| 踩点 | `manageList` 中 `marked=Y` 的数量 ≥ `max(raDislikes, min_dislikes)` |

里程校验用的是**截断后**的里程，不是任务表原始里程。

`start` 响应中 `canSport=N` 会抛 `RunNotPermittedError` 并带出 `recordId`，
**不会继续发送**。

### 5.2 自动真人化修正

旧抓包任务表有两类字段自相矛盾，脚本在**上传前**自动修正
（只改 `runTime` / `runStep`，必要时平滑 `runMileage` 的 GPS 瞬移，**坐标不变**）：

| 问题 | 实测 | 修正 |
|---|---|---|
| 步数按固定周期累加 | 9 张 fch 表折算 **357~642 spm** | 按实际时长重分配，目标 140~200 |
| `Δt=0` 但有位移 | tasklist_6 有 346/1179 段 | 时间轴按本表平均速度重建 |
| 单点 GPS 瞬移 | tasklist_3 有一处 **83 m/1 s** | 超出部分摊给邻段，总里程不变 |

每条修正打印 `[真人化]` 一行。已经合理的表原样通过（幂等），
非法输入仍在校验阶段原样报错。

**实测效果**：

| 指标 | 修正前 | 修正后 |
|---|---|---|
| 步频 | 357~642 spm | 148~200 spm |
| 步幅 | 0.35~0.56 m | 1.00~1.20 m |
| 速度越界区间 | 1%~30% | ≈0% |
| 总里程 | — | 完全不变 |

### 5.3 步频硬边界（40~300 spm）

1. **夹取**：每包 `runSteps`（split 体）与 `recodeCadence`（finish 体）
   发送前统一夹进 `[40, 300]`，越界打印 `[步频夹取]`
2. **分批边界避让**：单点包没有时长与位移，`runSteps` 只能是 0。
   若发完这批恰好只剩 1 个点，本批少发一个或整批并入尾批，
   保证**每个 split 包至少 2 点**

### 5.4 结束链

```
isStandard（状态检查）→ 尾批补发 → finish
```

- `isStandard` 与 `finish` 使用**同一份请求体**
- `isCheat=Y` 优先停止；仅 `isStandard=Y` 允许自动结束
- 检查失败、`isStandard` 非 `Y` 或 `isCheat=Y` → 尾批与 `finish` 都不发送

## 6. 轨迹自然化与合成

两条路径，都只做几何形变：

| 入口 | 用途 |
|---|---|
| GUI「轨迹自然化」 | 图形化预览 + 保存，推荐 |
| `--route-config` | 命令行，配置文件驱动 |

**不识别地图、不做路径规划、不判断道路是否可通行。**

### 6.1 GUI 自然化

见 §2.4。三档强度对应 `yun_route.NATURAL_STRENGTHS`。

### 6.2 命令行合成

```bash
python tools/generate_route.py --config examples/routes/deform_xc.json \
                               --output work_dir/route_preview.geojson
python main.py --route-config examples/routes/deform_xc.json
```

算法：按弧长重采样成 5.5m 等间距折线 → 法向 OU 低频游走 → 二维相关漂移
→ 稀疏指数衰减跳变 → 可选长度校准。

参数与一致性规则见 [ROUTE_GENERATION.md](ROUTE_GENERATION.md)。

> 合成模式对**要求踩点的任务**支持有限：需要轨迹实际经过打卡点，
> 覆盖不足会被拒绝。打表模式的任务表本身已包含踩点信息，更省事。

> **能力边界**：形变只改变几何与节奏，不改变轨迹的"可跑性"，
> 也不能证明服务端不会复核。重复使用同一来源（即使换种子）仍可能被识别。

## 7. 人脸核验任务

任务 `runFaceStatus=Y` 时的行为：

- **未提供人脸源**：立即停止（不默认放行）
- **提供 `--face-photo`**：需配合 `--face-detection` 标注，
  且标注必须用 `source_sha256` 绑定到该图片文件
- **提供 `--face-video`**：需逐帧标注，未标注帧视为无检测

**检测模型（RetinaFace）未移植**，标注必须人工提供，**没有检测结果时不放行**。

图像链：EXIF 摆正（仅 3/6/8）→ 宽 >720 缩到 720 → >150KB 走质量阶梯 80..20。

比对预算：`faceTime + 4s` 单调时钟，越界一律 `expired`。
首传 → ≤3 次立即重试（1s 间隔）→ 等待期每 3s 重发。

**人脸比对失败后不自动提交跑步数据**——这与 APK 行为不同，是刻意的策略偏差。

## 8. 常见异常

| 报错 | 原因 | 处置 |
|---|---|---|
| `HTTP -1 … RemoteDisconnected` | 学校地址失效 | 用 `tools/getUrl_Id.py` 重查，**不要猜端口** |
| `code=401` | token 失效 | 重新登录或更新 token |
| `code=500` | 版本过低或密钥配置错 | 检查 `app_edition`、`cipherkey*` |
| `生成步频不在任务允许范围` | offset 配置收窄了区间 | 把四项 offset 改为 0 |
| `打表里程 X km 不在任务范围` | 任务表里程与学校要求不符 | 换一张表，或调整 `max_mileage_km` |
| `打表步频 X spm 不在任务允许范围` | 同上 | 换表 |
| `任务表只标记了 N 个踩点` | 踩点数不足 | 换一张踩点足够的表 |
| `BusinessException` | 服务端明确拒绝 | 修数据/时机；后续请求一律不发 |
| `TransportOutcomeUnknown` | 传输结果未知 | **先查服务端记录**，勿盲目重发 |
| `FaceRequiredError` | 任务要求人脸但无源 | 用官方 App，或提供照片+标注 |

**连接失败先核对学校地址**：

```bash
python tools/getUrl_Id.py --list
python tools/getUrl_Id.py --school "你的学校全称" --write --config config.ini
```
